# 2026-11-10

## 跳过校验脚本改为批量流水线（解决逐条复核导致的性能问题）
- 用户反馈：每个种子都检查是否成功跳过校验，比以前慢太多。确认旧实现每种子有 2 处串行
  0.5s 轮询（`wait_until_removed` + `verify_skipped`），N 个等待窗口相加。
- 改造：`skip_reimport` 改分阶段流水线，每批「先全部 add 完，再整批统一复核」：
  导出落盘 → 一次批量 delete(`hashes` 用 | 分隔，已实测 HTTP 200) → 整批共享等待窗口
  → 逐个 add 不等待 → 收敛式批量复核（每轮只查未定论 hash）→ 少数未落地项整批重试。
- 新增 `query_states`（hashes 按 50 分片）、`wait_batch_removed`、`verify_batch`、`add_batch`、
  `chunked`；移除 `find_torrent`/`wait_until_removed`/`verify_skipped`/`reimport_and_confirm`。
- 消除 `run()` 里重复的全量 info 拉取：原 3 次 → 1 次（仅在确有改动后刷新）。
  全量 info 实测约 89MB / 9.8-28.9s，服务端 274 个种子同时校验时波动极大。
- 新增参数 `--batch-size`(默认 50，设 1 退化为逐条)、`--limit`(小样本试验，导出也遵守)。
- 可靠性加固（实测触发）：
  - 服务端高负载偶发 `ConnectionResetError(10054)` 与查询长尾（0.04-26.7s）
  - `query_states` 每分片重试 3 次，耗尽抛 `QueryUnavailable`
  - 查询故障标 `unknown` 并整批重试，不误判为种子失败
  - 轮询保证至少 `MIN_POLL_ROUNDS=2` 轮完整查询，防止长尾吃掉超时窗口
  - 超时放宽 30→60s
- 备份策略：删除前预落盘整批 .torrent；确认成功的自动清理，失败的保留留档。
- 验证：离线 mock 5 场景全过（常规分批/逐条退化/收敛查询/missing重试/查询故障），
  真实只读验证 `query_states` 179 hash 分片 0.11s 返回 179 条、状态一致；
  端到端预览导出正常。**未实际执行 --skip-check**（当前 178 个 checking 种子，避免误动）。
- 量化（N=283, batch=50）：delete 283→6 次；等待/复核查询 ≥566 次→约 12 次；
  串行 sleep ≈283s→≈6s；全量 info 3 次→1 次。
